# ADR-0005 — Чат создаётся по `chatId` из `CheckAccount`, а не по `phone@c.us`

- **Статус:** принято
- **Дата:** 2026-10-05

## Контекст

`SendMessage` в MAX и Telegram принимает и `chatId` (`"10000000"`), и номер (`"79991234567@c.us"`).
Но уведомления — и ответ собеседника, и статусы — всегда приходят с числовым `chatId`.

Если создать чат по `79991234567@c.us`, ответ придёт в «другой» чат `10000000`: в списке окажется
два чата с одним человеком, ответ не появится там, где пользователь его ждёт.

Документация дополнительно предупреждает:

- MAX (FAQ «Проверка и хранение идентификаторов»): безопасная стратегия — один раз получить
  `chatId` методом `CheckAccount`, хранить его, при `noAccount` — проверить заново;
- Telegram: статус `failed` с описанием «chatId unresolvable on this session» — «получите
  актуальный chatId методом CheckAccount».

## Решение

«Новый чат» = `CheckAccount(phoneNumber | username)` → чат с ключом `chatId` из ответа.

- MAX: только `phoneNumber`, номера РФ (`7` + 10 цифр) и РБ (`375` + 9 цифр) — проверяется на
  клиенте до запроса.
- Telegram: номер **или** `@username` (номер может быть скрыт настройками приватности).
- `exist: false` → понятная ошибка в форме, чат не создаётся.
- Входящее от `chatId`, которого нет в списке, но с тем же `senderPhoneNumber`, что у существующего
  чата, переносит этот чат на новый `chatId` (защита от устаревшего `chatId`).

## Последствия

- **+** Ответы и статусы всегда попадают в нужный чат.
- **+** Пользователь сразу узнаёт, что у номера нет аккаунта, а не после «тихой» неудачи.
- **−** Каждое создание чата тратит проверку: на тарифе «Разработчик» MAX их 100, а частые проверки
  мессенджер ограничивает (HTTP 469). Поэтому `CheckAccount` вызывается только по явному действию,
  без автопроверки при вводе.
