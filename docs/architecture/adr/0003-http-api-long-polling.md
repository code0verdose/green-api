# ADR-0003 — Получение через HTTP API: long polling, at-least-once, один опрашивающий на инстанс

- **Статус:** принято
- **Дата:** 2026-10-05

## Контекст

ТЗ: получение — по технологии HTTP API. По документации GREEN-API:

- `ReceiveNotification` отдаёт **одно** уведомление (FIFO) или `null` по таймауту `receiveTimeout`
  (5–60 с, по умолчанию 5);
- пока уведомление не удалено `DeleteNotification`, следующий вызов вернёт его же;
- очередь хранит уведомления 24 часа; лимит — 100 запросов/с на метод.

## Решение

Цикл `src/units/notification/lib/notification-poller.util.ts`:

```
receive(receiveTimeout = 20 с) → null ? повторить : обработать → delete(receiptId) → повторить
```

1. **Удаление после обработки** (at-least-once). Если вкладку закрыли между обработкой и удалением,
   уведомление придёт снова; обработчик идемпотентен — сообщения дедуплицируются по `idMessage`.
2. **Ошибка обработчика не блокирует очередь**: уведомление всё равно удаляется (иначе «ядовитое»
   уведомление заклинило бы приём навсегда), ошибка пишется в `console.warn` — и в проде: в ошибках
   нет URL, токен не утекает.
3. **Паузы при сбоях**: экспонента 1 → 2 → 4 … 30 с с джиттером ±20 %; сбрасывается после успеха.
   Пустой ответ быстрее 1 с (сервер или прокси не держит long poll) — пауза до 1 с, а не цикл
   со скоростью сети.
4. **Фатальные ошибки останавливают цикл**: 401/403 (токен), 400 «webhook url is set»,
   истёкший инстанс, 404 (неверный `apiUrl`). Повтор их не исправит; UI объясняет, что делать.
5. **Отмена**: `AbortController` прерывает висящий long poll при выходе и уходе со страницы.
6. **Один опрашивающий на инстанс**: Web Locks API (`navigator.locks`), имя замка — по `idInstance`.
   Две вкладки, опрашивающие одну очередь, делили бы уведомления между собой, и каждая видела бы
   только часть переписки. Остальные вкладки ждут замок (статус «Сообщения принимает другая
   вкладка») и получают историю через событие `storage`. Без Web Locks — деградация до
   «опрашивает каждая вкладка», а не поломка.

`receiveTimeout = 20` — компромисс: меньше пустых запросов, чем при 5 с, и ниже типичных таймаутов
прокси (30–60 с). Таймаут самого запроса — `receiveTimeout + 10 с`.

## Альтернативы

- **`useQuery` с `refetchInterval`** — не выражает «удалить после обработки» и паузы по типам
  ошибок; long poll с интервалом 0 TanStack Query не поддерживает.
- **Webhook** — требует публичного сервера (см. ADR-0001).

## Последствия

- Поллер — чистая функция без React, покрыт тестами на фейковых таймерах.
- В React он подключается одним `useEffect` (легитимная подписка на внешний процесс) в
  `use-notification-poller.hook.ts`; статус — во внешнем сторе, без `setState` в теле эффекта.

### Принятые ограничения

- **Нет пробуждения по `online` / `visibilitychange`.** После возврата сети цикл продолжит работу,
  когда закончится текущая пауза: до 30 с плюс разброс 20 %, то есть до 36 с. Для чата из ТЗ это
  допустимо. Пробуждение по
  событиям браузера можно добавить, не меняя контракт поллера.
- **Замок остаётся у вкладки после фатальной остановки.** При 401/403 вкладка выходит сама и
  отпускает замок. При остальных фатальных ошибках (webhook настроен, срок инстанса истёк, 404 из-за
  неверного `apiUrl`) остановленная вкладка держит Web Lock, пока пользователь не нажмёт
  «Повторить» у индикатора, не выйдет или не закроет её. Другие вкладки того же инстанса опрос не
  перехватывают, но и не помогли бы: эти ошибки касаются всего инстанса, и повтор у них упал бы так
  же.
