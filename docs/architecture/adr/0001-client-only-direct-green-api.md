# ADR-0001 — Клиентское приложение без бэкенда, прямые вызовы GREEN-API

- **Статус:** принято
- **Дата:** 2026-10-05

## Контекст

ТЗ требует веб-интерфейс, который сам отправляет сообщения (`SendMessage`) и сам получает их
(`ReceiveNotification` / `DeleteNotification`). Учётные данные вводит пользователь на сайте.
Вопрос: нужен ли свой сервер между браузером и GREEN-API.

## Проверено замером

```
curl -i -X OPTIONS https://4100.api.green-api.com/waInstance…/getStateInstance/… \
  -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: GET'
→ HTTP/2 204, access-control-allow-origin: *, allow-methods: GET, POST, OPTIONS, DELETE,
  allow-headers: … Content-Type …
```

Тот же ответ у `api.green-api.com` и `3100.api.green-api.com`. Значит браузер может вызывать
все шесть нужных методов напрямую, включая `POST` с JSON и `DELETE`.

## Решение

Чисто клиентское SPA, статический хостинг на отдельном домене (ADR-0004, «Хостинг»). Все запросы идут из браузера в хост
`apiUrl` инстанса через собственный тонкий клиент (`src/shared/api/green-api.client.ts`).

## Последствия

- **+** Нулевая инфраструктура, деплой — статические файлы; соответствует ТЗ дословно.
- **+** Токен не проходит через третью сторону (наш сервер), только браузер → GREEN-API.
- **−** Токен живёт в браузере. Митигации — в ADR-0004 (sessionStorage, CSP, белый список хостов).
- **−** Webhook-доставка невозможна (нужен публичный сервер) — используется HTTP API, как и требует ТЗ.
- Если проект вырастет в продукт — добавляется бэкенд-прокси (roadmap → Later), клиент меняется
  только в одном месте: фабрике `createGreenApiClient`.
