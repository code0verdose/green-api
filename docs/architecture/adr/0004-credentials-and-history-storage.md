# ADR-0004 — Где хранятся токен и история переписки

- **Статус:** принято (пересмотрено после аудита безопасности)
- **Дата:** 2026-10-05

## Контекст

Бэкенда нет (ADR-0001), поэтому `apiTokenInstance` неизбежно находится в браузере. Уведомления
удаляются из очереди GREEN-API после получения: без локального хранения перезагрузка страницы
стирала бы переписку.

Первая версия этого ADR опиралась на три посылки, которые аудит безопасности опроверг замерами:
«токен не остаётся в браузере», «CSP не даёт вывезти токен», «до квоты localStorage далеко».
Ниже решение на проверенных посылках.

## Решение

| Данные                                                                   | Где                                                                                       | Почему                                                                                  |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Учётные данные (`messenger`, `idInstance`, `apiTokenInstance`, `apiUrl`) | `sessionStorage` вкладки                                                                  | переживают перезагрузку вкладки; не попадают в localStorage и в другие вкладки          |
| История чатов                                                            | `localStorage`, **свой ключ на инстанс**: `green-api-chat:chats:<messenger>:<idInstance>` | переживает перезагрузку; две вкладки с разными инстансами не трогают историю друг друга |
| Выбранный мессенджер                                                     | `localStorage`                                                                            | только тема экрана входа, не секрет                                                     |

Какой инстанс показывает вкладка — состояние в памяти вкладки, не в хранилище.

### Выход

| Событие                                   | Токен                                                          | История на устройстве               | Другие вкладки того же инстанса |
| ----------------------------------------- | -------------------------------------------------------------- | ----------------------------------- | ------------------------------- |
| «Выйти»                                   | удаляется                                                      | удаляется                           | получают сигнал и выходят       |
| 401/403 от API (токен сменили в кабинете) | удаляется                                                      | **сохраняется** до следующего входа | —                               |
| Закрытие вкладки без «Выйти»              | остаётся в файлах профиля браузера до очистки сессии браузером | сохраняется                         | —                               |

### Защита токена

1. **`cache: 'no-store'`** у всех запросов. GREEN-API не присылает `Cache-Control`, а токен — часть
   URL, поэтому без этого ответы (и токен в ключе записи) ложились в HTTP-кеш профиля на диске.
   Замер: с `no-store` записи в кеше нет.
2. **Белый список хостов** для `apiUrl`: только `https://<поддомен>.green-api.com` /
   `<поддомен>.greenapi.com`, без порта, логина, query и hash. Проверяется и при вводе, и при
   чтении сессии из `sessionStorage` — подложенная сессия с чужим хостом отбрасывается.
3. **Токен кодируется** (`encodeURIComponent`) при подстановке в путь и не попадает в ошибки,
   тосты и логи: `GreenApiError` не содержит URL, тело ошибки очищается от токена.
4. **Нет HTML из данных**: текст сообщений — React-текст, нет `dangerouslySetInnerHTML`.
5. **CSP** в продакшен-сборке: `script-src 'self'`, `connect-src` только хосты GREEN-API.
   CSP **снижает вероятность внедрения** чужого скрипта, но **не мешает вывезти** токен уже
   выполняющемуся скрипту: навигация не ограничена, а `connect-src` пропускает любой инстанс
   GREEN-API, в том числе инстанс атакующего. Поэтому главная защита — отсутствие XSS (п. 4).
6. `<meta name="referrer" content="no-referrer">` — адреса вида `/chats/<номер>` не уходят
   в заголовке Referer на внешние ссылки (личный кабинет GREEN-API).

### Защита истории

- Данные из хранилища — граница доверия: разбираются Zod-схемой **по записи**. Испорченный чат или
  сообщение выбрасывается один, остальная история остаётся.
- Идентификаторы чатов ищутся только среди собственных ключей (`Object.hasOwn`): адрес
  `/chats/constructor` не находит `Object.prototype` и не портит историю.
- Квота localStorage (~5 млн символов на origin в Chromium) **достижима**: ~200 символов служебных
  данных на сообщение, 30 чатов × 500 сообщений уже близки к пределу. При первом
  `QuotaExceededError` история урезается до 100 последних сообщений каждого чата и записывается
  снова. Дальше каждая запись урезается заранее, без заведомо неудачной попытки записать всё. Если
  не помещается и урезанная история, приложение работает в памяти. Каждый вид проблемы («урезано»,
  «не сохраняется», «хранилище заблокировано») показывается пользователю один раз, и более
  серьёзная проблема не прячется за уже показанной.
- Вкладки одного инстанса **сливают** историю, а не перезаписывают друг друга: сообщение, принятое
  между двумя записями, не теряется. Правила слияния:
  - сообщения объединяются по `localId`, а одно сообщение GREEN-API (`idMessage`) — один пузырь,
    даже если копия отправителя и эхо API пришли в разные вкладки;
  - у каждого сообщения есть ревизия `rev`, которую увеличивает каждое изменение статуса на этом
    клиенте. Из двух копий одного пузыря (один `localId`) побеждает бо́льшая ревизия, ранг статуса
    решает только при равенстве. Поэтому
    «Повторить» в одной вкладке не откатывается вкладкой, где ещё лежит «не отправлено», а
    «прервано закрытием страницы» побеждает зависшее «отправляется» из живой вкладки;
  - при равных ревизии и статусе побеждает сохранённая копия;
  - у дубля по `idMessage` (копия отправителя и эхо API из разных вкладок) ревизии несравнимы:
    их меняли разные вкладки. Побеждает дальний статус, ревизия решает только при равенстве.
    Победитель встаёт на место первой копии, забирает её `localId` и наибольшую ревизию из двух,
    поэтому вторая вкладка узнаёт его и не оставляет свою устаревшую копию отдельным пузырём, а
    «доставлено» не теряется после «Повторить»;
  - порядок — сначала сохранённая история, потом то, чего в ней нет. Свои сообщения, стоящие до
    первого общего с сохранённой историей, не возвращаются: их выбросило ограничение в 500 сообщений
    или урезание при переполнении, а возврат перемешал бы ленту;
  - каждая вкладка пишет свои изменения, а в ответ на чужую запись пишет обратно, только если
    слитая история содержит то, чего в сохранённой нет: чат, более позднюю активность, сообщение
    или более свежую ревизию (`addsToStored`, сравнение по ссылке на объект). Порядок ключей,
    ограничение и урезание новостью не считаются;
  - **предохранитель:** не больше одной обратной записи между двумя собственными изменениями
    вкладки (`canWriteBack`). Обмен записями конечен по построению, даже если правила слияния
    где-то ошибутся или рядом открыта вкладка со старой сборкой. Остальное, чего не хватает
    хранилищу, уйдёт со следующей своей записью. Цена: если соседняя вкладка дважды запишет
    раньше, чем до неё дойдёт событие (миллисекунды), а опрашивающая вкладка закроется до своей
    следующей записи, последнее принятое ею сообщение останется только в памяти и пропадёт с ней;
  - удаление ключа истории (выход в другой вкладке) не сливается: выход доводит сигнал выхода.

## Хостинг: только отдельный origin

Хранилище браузера делится по origin. На общем origin вроде `https://<owner>.github.io` все
Pages-сайты аккаунта видят localStorage/sessionStorage друг друга и могут держать Web Lock этого
приложения, а `script-src 'self'` пропускает их скрипты. XSS в любом соседнем сайте стал бы XSS
здесь. Поэтому приложение публикуется только на отдельном origin — на сервере и домене владельца
(STORY-001-04). Деплой на GitHub Pages аккаунта отклонён.

## Последствия

- **−** XSS в будущем коде дал бы доступ к токену. Полностью токен из браузера убирает только
  бэкенд-прокси (roadmap → Later).
- **−** История хранится на устройстве в открытом виде; «Выйти» её удаляет.
- **+** Смена токена в кабинете не стоит пользователю переписки.

### Принятые ограничения истории

- **Слияние не умеет удалять.** Если вкладка перенесла чат на новый `chatId` (ответ пришёл с другим
  идентификатором того же номера), вторая вкладка с открытой старой историей вернёт чат под старым
  `chatId`. Получится две строки одного собеседника. Сценарий редкий и данных не теряет; лечится
  перезагрузкой второй вкладки до переноса либо надгробиями (tombstones) в формате хранения.
- **Нет `migrate` в persist.** Ревизия `rev` добавлена без смены `CHAT_STORAGE_VERSION`: запись без
  неё читается как `rev: 0`. Если версию когда-нибудь поднять без функции миграции, история прежней
  версии будет **стёрта**: zustand отдаст пустое состояние, и первая же запись затрёт старое. Перед
  сменой формата нужны `migrate` и проверка «в хранилище версия новее моей», чтобы вкладка со
  старой сборкой не писала поверх новой, а предлагала перезагрузку. Пока релизов не было, вкладок
  со старой сборкой у пользователей нет; предохранитель обратной записи ограничивает вред одной
  записью на собственное изменение.
- **Две реальные отправки, один пузырь.** Если первая попытка дошла до сервера, хотя ответа не было
  («могло уйти»), а пользователь нажал «Повторить» в другой вкладке, собеседник получит два
  сообщения. На экране останется один пузырь: эхо первой попытки подхватывается пузырём «не
  отправлено», а повтор отмечает тот же пузырь своим `idMessage`. Текст «могло уйти» об этом и
  предупреждает.
- **Открытие новой вкладки во время отправки.** Новая или перезагруженная вкладка считает
  «отправляется» из хранилища прерванным и помечает его «не отправлено» с новой ревизией. Если в
  этот момент запрос ещё идёт в живой вкладке (до 15 с таймаута), её пузырь тоже покажет «не
  отправлено», пока не придёт ответ. «Повторить» в этом окне даст дубль. Отличить живую вкладку от
  закрытой можно Web Lock на каждую отправку — это следующее улучшение.
- **Истории других инстансов не вытесняются.** После 401 или закрытия вкладки история инстанса
  остаётся на устройстве и делит квоту с активной. Урезание при переполнении касается только
  активного инстанса.
